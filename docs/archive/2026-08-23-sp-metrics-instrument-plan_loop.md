## 1. What this file is

This is the orchestration plan compiled from `docs/plans/2026-08-23-sp-metrics-instrument-plan.md` by the loop-drive drive-compile dispatch.
One frontier-model session drives it end to end: it launches each wave, gates on the executed checks and verdicts, merges, and advances, without a human pasting prompts.

The source plan stays ground truth for what each unit must produce; where this file and the source plan disagree on a unit's contract, the source plan wins and this file is corrected.
No task in this plan fires a live model call or incurs API spend; the live passes (pass 1 and pass 2) are downstream of ticket #8 and out of scope here.

```
orchestrator (this session, Opus, never a worker)
  |
  Wave 1  ringer manifest wave1.json  (max_parallel 3)
  |   T1 seed+isol   T2 metrics*   T3 scans   T4 blinding   T5 mining
  |   -> per-task executed check (primary gate) -> orchestrator gate

  |   -> executed check -> orchestrator adversarial review -> gate
  |
  Wave 3  ringer manifest wave3.json  (T7 tracer*, depends on T1-T6)
      -> executed check -> orchestrator adversarial review -> gate
      -> final-wave advisory /loop-review

  * gate-critical: additional adversarial review at the gate
```

Three validation layers, every unit:

1. Implementer self-check: the worker writes the failing selftest first, then implements until its own `--selftest` and the source-plan acceptance pass. This is the worker's loop, not a gate.
2. Per-unit executed check: the manifest `check` (Section 8) is the primary gate. It lives in the manifest, outside every worker's file ownership, reruns the acceptance command, and asserts substance on real or check-controlled data (not just exit codes of worker-authored scripts). Exit 0 is the only PASS.
3. Orchestrator gate: ringer's post-run ritual (run JSON is truth, read every retried or failed log, spot-check a passing artifact), plus the adversarial diff review for the gate-critical units.

## 4. Hazard mitigations

Check custody (all units).
No unit lists any acceptance-check wrapper among its owned files; the manifest `check` is the attack surface and lives in the manifest, which no worker can reach.
Consequence carried from the source plan: several units are only verifiable by running the very script the worker authored (a metric extractor is testable only by running it).
That is legal because the script is the deliverable, but each manifest check independently asserts on external or check-controlled evidence so a check-free stub cannot pass:
T1 independently re-hashes the five shared-state files around the isolation run and greps the worker script for real hashing (no `echo isolation: ok` stub survives);
T2, T3, T5 assert the real-transcript output schema through a check-owned Python one-liner;
T4 asserts three written files and a no-leak grep over anonymized text;
T6 feeds a check-owned 12-row-versus-11-row log through `--validate-log`.

Deviation from the source plan (worker commits).
The source plan ends each task with a `git commit`.
Under ringer `worktrees: true` a passing worktree is deleted and worker commits die with it, so the specs instruct the worker to leave changes uncommitted and every check exports a patch with `git add -A && git diff --cached > <path-outside-worktree>.patch`; the orchestrator applies and commits on the integration branch at the gate.

Ringer footguns carried from `references/ringer-substrate.md`.
Deliverable loss on a passing worktree is handled by the patch export above and by `expect_files` (harvested to the artifact store, surviving deletion).
Gitignored outputs missing from a patch export: flagged explicitly for Wave 3, because T7 MODIFIES `.gitignore` to add `pilot/**` ignore rules.
`git add -A` cannot stage ignored files, so T7's spec forbids placing any deliverable under the new ignore globs (the dry-run writes scratch to a mktemp dir outside the repo), and T7's check verifies the `.gitignore` edit itself appears in the exported patch.
Engine-concurrency staggering: not triggered here (the claude-zai lane is used, not opencode's shared sqlite), so no stagger is needed; if a unit is ever re-routed to opencode, cap `max_parallel` or stagger the spawns.

Two accepted lint warning families (do not "fix" by gutting checks).
`ringer.py lint` emits two families for every wave: "deliverable would be deleted with the worktree" (fires on any repo-relative `expect_files` under worktrees mode) and "check runs <script>, which the task also owns".
Both are inherent to this build: `expect_files` list the real deliverables for the results page and the checks must run the worker-authored scripts to verify them.
Both are mitigated (patch export; independent substance assertions) and are the exact check-custody consequence the source design calls out.
They are non-blocking warnings at `run` time; the driver leaves them in place.

Disjoint files (Wave 1).
The five Wave-1 units own disjoint files by construction, so a merge conflict at the gate is a scope violation, not something to quietly resolve.

Not-portable checks ($HOME state).
The acceptance checks read `$(ls -t ~/.claude/projects/*/*.jsonl | head -1)` and hash `~/.claude.json` and the tweakcc files.
Ringer workers run locally against the same $HOME, so this works, but the checks are not portable to another machine and depend on at least two assistant-bearing transcripts existing under `~/.claude/projects`.

Use the SAME `run_name` `sp-metrics-instrument` for all three waves.

Per wave:

1. Launch.
   Write the wave's manifest (Section 8) to disk and run `cd /Users/jjrdar/repos/ringer && ./ringer.py lint <manifest> && ./ringer.py run <manifest> --identity loop-drive`.

   Consume the run JSON in `~/.ringer/runs/` (it is truth; a background shell's exit status is transport and can lie).

   For the gate-critical units (T2, T6, T7) run the additional adversarial review below before advancing.

   If the worker's output was correct and the CHECK was wrong, fix the check, commit the audited work, and annotate `docs/MODEL-NOTES.md` in the ringer repo; do not burn a retry.
   If the worker was wrong, a small spec fix relaunches that unit (see slip rules); a design issue is recorded for the downstream review.
   Write the wave summary and the `AGENT STATUS` gate receipt.

   Turn any repeated failure pattern into a spec or check fix before the next wave.
