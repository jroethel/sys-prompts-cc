# Brief: upgrade and drift policy for SP packs when the pinned version moves (wayfinder #10)

Ticket: https://github.com/jroethel/sys-prompts-cc/issues/10
Shaped 2026-08-23 via /loop-brainstorm. One-Minute Test verdict: ONE AGENT.
Revised same day after a single Rubix lens A review (harness-engineer seat, fresh context). All 10 findings incorporated.

## Outcome

When the pinned Claude Code version moves, Jeremy can carry the designated SP pack forward with confidence.
Every override is mechanically classified as safe-to-carry or needs-eyes, and review time is spent only on the needs-eyes list.
Presupposition verdict: the issue presupposed drift is decidable by normalized-content hash and similarity ratio.
The #3 diff-surface measurements verified that presupposition, so it holds.
Constraint inherited from #9: the live install's patch-state is not stable across a session, so the policy never reads live install state.
Molt inputs are committed corpora, committed provenance, a committed pack pointer, and external sources of record only.

## End artifact

The executed first molt: a committed report classifying the lobotomized pack across 2.1.204 to 2.1.241, with review-class findings landed as a GitHub issue.
This is the repeatable half of the first domino (the confident upgrade from pinned 2.1.204 to current Claude Code).

## Done looks like

- `just pin-target <V>` ends with the molt against the previous pin: retro-check ask first, classification summary printed, report committed, issue opened only if review-class findings exist.
- A standalone re-run of the same molt from committed corpora is possible and deterministic.
- The 2.1.204 to 2.1.241 report exists in the repo, and its review issue is open if the run produced review-class findings.

## Decisions taken in this sitting

| Decision                                 | Choice                                                |
| ---                                      | ---                                                   |
| Pack scope                               | Whatever pack is designated by a committed pointer    |
| Trigger                                  | End of every `just pin-target`                        |
| Review line                              | Strict hash after alignment, no ratio threshold       |
| Cross-version alignment                  | Id-join with a normalized-content-hash bridge (#3)    |
| Extractor provenance                     | Recorded for every rung, extractor change is its own  |
|                                          | drift class, held constant across compared corpora    |
| Alert landing                            | Committed report plus auto-opened issue               |
| Provenance mismatch handling             | Flag and continue, acquisition keeps hard-fail        |
| Retro-check scope                        | Any externally-unverified pin, ask at molt-run start  |
| Molt inputs during classification        | Committed corpora only, never triggers acquisition    |
| First molt in scope (2.1.204 to 2.1.241) | Yes, part of this ticket's deliverable                |

Alignment comes first: prompts are joined across versions by id, with a normalized-content-hash bridge for ids the extractor re-segmented or renamed (the #3 method).
A raw id-count delta is not itself drift: the committed corpora jump from 1537 to 5072 prompt files across 2.1.204 to 2.1.241, and that jump is overwhelmingly re-segmentation, not new behavior.
The id namespace belongs to the extractor, not the Claude Code version, so provenance records the extractor identity on every rung (including cache), and an extractor change between compared corpora is flagged as its own drift class, distinct from content drift.

The verdict table, applied per override after the alignment bridge:

| Case                                                | Verdict                            |
| ---                                                 | ---                                |
| Mirror (override = old stock), underlay unchanged   | auto-realign                       |
| Mirror, underlay changed                            | auto-realign, listed in report     |
| Rewrite, underlay unchanged                         | carry forward silently             |
| Rewrite, underlay changed, override = new stock     | converged, auto-realign to mirror  |
| Rewrite, underlay changed, override differs both    | REVIEW                             |
| Suppression, target id present in new stock         | carry forward silently             |
| Suppression, target absent after bridge             | REVIEW (prompt may resurrect)      |
| Rewrite orphan (id and content absent after bridge) | REVIEW                             |
| Segmentation remap (content found under new id)     | auto-remap, counted in report      |

The comparison is three-way: override vs old stock, old stock vs new stock, and override vs new stock.
The third leg exists because #3 measured 185 lobotomized overrides authored against revisions newer than 2.1.204: when upstream converges toward an override, it has become a mirror at the new pin and earns auto-realign, not review.
Mirror auto-realign assumes the pack's mirrors are non-authoritative catalog copies, so a mirror whose underlay changed is still listed in the report (never silently overwritten) in case it was an intentional text-pin.
The report also carries an informational section of new-in-new-stock ids with no override counterpart, so the upgrade decision sees what Anthropic added, not only what the pack touches.

Retro-check defined: for any pin whose corpus was single-sourced without external validation at pin time (a cache or local extraction with no skrabe counterpart yet), compare skrabe's later-published JSON against the frozen local corpus.
A mismatch becomes a review-class flag, and the run still completes.
The ask fires at molt-run start because intent forks the answer: verifying robustness earns a yes, racing toward a newer version earns a skip.

## Approach

Chosen: A, a deterministic corpus-to-corpus classifier bolted onto pin-target.
The molt check is a pure function of committed inputs: old pinned corpus, new pinned corpus, designated pack.
Classification never hits the network or triggers acquisition, which is what makes the deterministic re-run claim true.
The retro-check is the one network touch, and it stays confined behind the opening ask.
Every override gets exactly one verdict from the table above.
The report is committed per bump, and an issue is auto-opened only when the review class is non-empty.
No judgment lives inside the tool.
Judgment is spent at the review issue, only on flagged items.

Considered B: a full molt session per bump (loop-molt pattern: worktree, drift ledger, staged merge gates, session-reviewed overrides).
Declined as the default because it needs A's classifier inside it anyway and its per-upgrade cost does not scale to the release cadence.
Its vocabulary survives in the report shape, and a heavy review can still escalate into a full session by Jeremy's call at the review issue.

Considered C: version-tag pre-filter, diffing only tag-changed prompts.
Declined on #3's evidence: tags agreed with content on only 190 of 399 aligned prompts and drift independently of the text.
Content hash decides, and tags at most rank.

## Success criteria

1. `[executed-check]` The first molt run (2.1.204, 2.1.241, lobotomized pack) completes and every applicable override carries exactly one verdict from the table.
2. `[executed-check]` Two runs on the same inputs produce identical reports, modulo timestamp.
3. `[executed-check]` The report separates segmentation remaps from true orphans, and the review class contains no override that hash-equals the new stock.
4. `[executed-check]` Review count above zero opens exactly one issue linking the report, and review count zero opens none.
5. `[executed-check]` An externally-unverified pin triggers the retro-check ask, accepting diffs skrabe's published JSON against the frozen corpus, and a mismatch lands as a review-class flag while the run still completes.
6. `[executed-check]` The molt run succeeds with the live install's symlink and config untouched and unread, verified by running under an environment where dereferencing them would fail.
7. `[executed-check]` Each review-class report entry carries the stock old/new diff and the override prose inline.
8. `[judgment]` Jeremy's spot-check of a sample of first-molt verdicts agrees with the classifier. Reformulation attempted: the full-population structural check is criterion 1, and agreement with Jeremy's judgment is irreducibly human.

## Seams

Blast-radius order, each independently checkable:

1. Alignment bridge: cross-version id join with content-hash fallback, remaps and true orphans separated.
2. Stock-drift table: per-aligned-prompt underlay comparison between two pinned corpora.
3. Pack overlay verdicts: the verdict table applied to a pack against that stock-drift table.
4. Report and issue emission from a verdict set.
5. Retro-check sweep driven by provenance.
6. pin-target integration, including extractor-identity provenance on every rung.

## Known vs guessed

Verified this session:

- Both corpora and their provenance records are committed, and both pins are provenance rung cache with no extractor identity recorded.
- The acquire-corpus stock-content check only guards 2.1.204 (read in the script), so a cached corpus for any other version is adopted without external validation - the gap the redefined retro-check closes.
- The corpora jump from 1537 to 5072 prompt files (provenance counts), so cross-version alignment cannot be a naive id join.
- Collision files (id plus content-hash suffix) exist in corpora/2.1.204, so one-text-per-id does not hold.
- #3's decidability numbers (normalization takes Piebald agreement from 41% to 99%, tags unreliable, 185 lobotomized overrides authored against newer revisions).

Believed, unchecked:

- Skrabe keeps publishing at the same URL pattern and eventually catches up to new versions.
  If wrong, the retro-check idles and unverified pins stay single-sourced, while the molt itself is unaffected.
- The lobotomized pack's files are on disk where the first molt can read them (not located this session).
  If wrong, the first run blocks until the pack pointer is resolved.
- The lobotomized pack's mirrors are non-authoritative catalog copies, not intentional text-pins.
  If wrong for some file, the report listing (not silent auto-realign) is what catches it.

Guessed:

- Future Claude Code versions stay extractable by the tweakcc extractor.
  If wrong, pin-target fails before any molt, blocking the upgrade but not corrupting the policy.
