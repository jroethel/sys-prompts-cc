Three validation layers, every ringer unit:

1. Implementer self-check: the worker writes the failing `--selftest` first, runs it to see it fail, then implements until it passes. This is the worker's loop, not a gate.
2. Per-unit executed check: the manifest `check` (Section 8) is the primary, non-negotiable gate. It lives in the manifest, outside every worker's file ownership, reruns the selftest, and greps for pinned verbatim assertions so a gutted selftest cannot pass. Exit 0 is the only PASS.
3. Orchestrator gate: ringer's post-run ritual (run JSON is truth, read every retried or failed log, spot-check a passing artifact), plus the adversarial diff review for T3, T6, T7 under the reviewer conduct contract and verdict discipline in Section 6.

T8's layers are the executed verification script (criteria 1-7) and Jeremy (criterion 8); there is no third layer because the orchestrator IS the implementer for that unit.

## 4. Hazard mitigations

Check custody and the selftest question.
No unit's ownership list includes its own acceptance-check script; the manifest `check` is the attack surface and lives in the manifest, which no worker can reach.
The source plan's acceptance checks are `python3 scripts/molt_*.py --selftest`, and the selftest code is part of the file the worker writes, so a worker could in principle gut the selftest and print the ok line.
This stays legal because the selftest blocks are pinned VERBATIM in the source plan (spec content, not worker judgment), and each manifest check is an orchestrator-side executed command that both runs the selftest asserting exit 0 plus the pinned `<module> selftest: ok` line AND greps the file for distinctive pinned assertion lines from the verbatim block, so a stub or rewritten selftest fails the check.
`ringer.py lint` will still warn "check runs a script the task owns" on every task; that warning is inherent to this design, mitigated as above, and left in place - do not "fix" it by weakening checks.

Deviation from the source plan: worker commits removed.
The source plan ends each task with a `git commit`.
Under run-level `worktrees: true` a passing worktree is DELETED and worker commits die with it, so every spec instructs the worker to leave changes uncommitted, every check exports a patch (`git add -A && git diff --cached > <workdir>/<key>.patch`), and the orchestrator applies and commits on the integration branch at the gate, using the source plan's commit messages.

Deviation from the source plan: specs point at the committed plan for verbatim blocks.
Ringer specs are normally fully self-contained with no pointer specs.
Here each spec carries the role, boundary, ownership list, interface summary, hard rules, and how-to-run inline, but points at the committed source plan section (repo-relative path, present in every worktree since commit dc4158a) for the full interface contract, behavior notes, and the verbatim selftest block.
That is source MATERIAL, not instructions, which ringer's spec rules permit; it was chosen over full embedding to keep specs under glm-5.2's long-spec stall ceiling (MODEL-NOTES 2026-07-08) and this file streamable.
Lint may nudge; the pointer is deliberate.

Deviation from the source plan: T1 Step 5 moved to the check.
The real-pack-ref verification (manifest ref resolves in `~/repos/lobotomized-claude-code`) runs in T1's manifest check, not as a worker step; verified at compile time already (ref `e0e969b...347d` resolves, variant `system-prompts-opus-4-8` present at that ref).

corpora/ is gitignored and untracked (compile-time finding, drives two mitigations).
`git ls-files corpora` returns zero entries and `.gitignore` line 2 is `corpora/`, while `corpora-provenance/` IS tracked.
So worker worktrees contain NO real corpora - harmless for T1-T7, whose selftests are all synthetic temp fixtures with zero network, and one reason T8 (which needs the real on-disk corpora) runs in the orchestrator's lane in the real checkout.
It also contradicts the plan's and brief's "committed corpora" premise; see the spec-gap list in Section 6 - the driving session gates on this at pre-flight.

Ringer footguns carried from `references/ringer-substrate.md`.
Deliverable loss on a passing worktree: handled by the patch export plus `expect_files` (harvested to the artifact store).
Gitignored outputs missing from patch exports: no worker deliverable lands under an ignored path (all are `scripts/`, `config/`, `justfile`); `docs/molt/` output belongs to T8 in the real checkout, so the footgun does not fire.
Engine-concurrency staggering: not triggered (claude-zai lane, not opencode's shared sqlite); if any unit is ever re-routed to opencode, cap `max_parallel` or stagger.

Disjoint files.
Wave 1's three units own disjoint files by construction; wave 5's T7 (`justfile`, `scripts/acquire-corpus.sh`) and T8 (`docs/molt/` output) are disjoint per the source plan.
A merge conflict at any gate is a scope violation, not something to quietly resolve.

Shared append-only files: none in the source plan, so no per-unit log conversion is needed; ringer's own per-task logs in `<workdir>/logs/` are the unit logs.
