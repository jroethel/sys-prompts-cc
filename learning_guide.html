Project summary and scope

This guide captures the drift-policy vocabulary and the retro-check gap shaped during the #10 sitting.
Wayfinder #10 decides what happens to SP override packs when the pinned Claude Code version moves: what re-runs, what auto-realigns, what demands review.
Surfaced 2026-08-23 in the /loop-brainstorm sitting for issue #10; Jeremy asked for the terminology and diagram to be captured here.

Terminology (defined as synonym pairs)

Live install = the daily driver.
The binary ~/.local/bin/claude points at. Its patch-state is unstable (#9 watched it flip stock, then Jeremy's --restore, then re-lobotomized), so drift policy never reads it. Molt inputs are committed corpora plus external sources only.
Pinned version = frozen snapshot.
A version whose prompt corpus is committed under corpora/<V>/ with a provenance record in corpora-provenance/<V>.json. Two exist: 2.1.204 (baseline = the old pin) and 2.1.241 (target = the new pin, the version being upgraded toward).
Corpus = prompt snapshot.
The normalized per-prompt markdown extracted from one version's binary, keyed by tweakcc extractor id.
Skrabe published JSON = external second opinion.
Someone else ran the same extractor and published prompts-<V>.json; a source of record to check the local copy against.
Rung = which source the pin came from.
Rung 1 cache (= reuse what was saved before), rung 2 skrabe (= adopt the published second opinion), rung 3 local extraction (= run the extractor yourself; no second opinion exists yet).
Retro-check = the delayed second opinion.
Once skrabe publishes a version that was pinned at rung 3, compare their JSON against the frozen local corpus. A mismatch flags for review; it never halts the run.

Key decisions register (2026-08-23 sitting, so far)

DecisionAlternatives consideredWhy
Drift policy governs whatever pack a committed pointer designates, keyed on tweakcc id Own future packs only; also governing Piebald; "applied" pack read from live state Pack-agnostic contract covers the lobotomized pack today and Jeremy's tailored packs later; Piebald stays a research reference. "Designated" not "applied": knowing what is applied would mean reading live install state, which the #9 constraint forbids (Rubix finding 9).
Molt check runs at the end of every just pin-target Separate on-demand recipe; checklist only Cannot be forgotten, adds no hooks or daemons, and stays re-runnable from committed corpora.
Review line is strict hash: any rewritten or suppressed override whose stock underlay changed at all demands review Ratio threshold (>= 0.97 auto-realigns); nothing silent #3 showed normalization already absorbs representation noise, so a ratio threshold would only swallow real wording changes.
Review-class findings land in a committed molt report plus an auto-opened GitHub issue Report only; issue only Matches GitHub-as-source-of-truth and makes an unreviewed molt visible in the tracker.
Provenance mismatches flag and continue; only new-corpus acquisition keeps hard-fail checks Hard-fail everything A late skrabe publication with a trivial diff should not block unrelated upgrades.
Retro-check covers any externally-unverified pin (cache or local extraction with no skrabe counterpart at pin time), firing at molt-run start as an ask, not an auto Fully automatic sweep; manual recipe; never; rung-3 pins only Jeremy: verifying robustness earns a yes; racing toward a newer version earns a skip. The prompt keeps the choice visible without forcing the cost. Scope widened from rung-3-only after the Rubix review verified both committed pins are rung cache, which the original scope would not have covered (finding 3).
#10's deliverable includes executing the first real molt (2.1.204 to 2.1.241, lobotomized pack) Policy only, execution as its own ticket A policy that has never classified a real pack rests on no executed check.

User preferences (carry into future sessions)

When a design question involves several similar-sounding states, present an ASCII diagram in session chat plus terminology defined as synonym pairs before asking the question.
Jeremy answered the retro-check question only after the diagram and synonym-pair glossary; he called the diagram helpful and asked for it to be captured here.
Surfaced 2026-08-23 when the round-2 retro-check question landed unclear on first ask.
Automatic sweeps that add cost to a run he triggers should be asks, not autos, when his intent forks the answer.
Verify-and-harden intent means run the sweep; move-fast-to-new-version intent means skip it. Design prompts around the intent fork instead of picking one default silently.
