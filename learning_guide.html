Project summary and scope

This guide captures the drift-policy vocabulary and the retro-check gap shaped during the #10 sitting.
Wayfinder #10 decides what happens to SP override packs when the pinned Claude Code version moves: what re-runs, what auto-realigns, what demands review.
Surfaced 2026-08-23 in the /loop-brainstorm sitting for issue #10; Jeremy asked for the terminology and diagram to be captured here.

Terminology (defined as synonym pairs)

Live install = the daily driver.
The binary ~/.local/bin/claude points at. Its patch-state is unstable (#9 watched it flip stock, then Jeremy's --restore, then re-lobotomized), so drift policy never reads it. Molt inputs are committed corpora plus external sources only.
Pinned version = frozen snapshot.
A version whose prompt corpus is committed under corpora/<V>/ with a provenance record in corpora-provenance/<V>.json. Two exist: 2.1.204 (baseline = the old pin) and 2.1.241 (target = the new pin, the version being upgraded toward).
Corpus = prompt snapshot.
The normalized per-prompt markdown extracted from one version's binary, keyed by tweakcc extractor id.
Skrabe published JSON = external second opinion.
Someone else ran the same extractor and published prompts-<V>.json; a source of record to check the local copy against.
Rung = which source the pin came from.
Rung 1 cache (= reuse what was saved before), rung 2 skrabe (= adopt the published second opinion), rung 3 local extraction (= run the extractor yourself; no second opinion exists yet).
Retro-check = the delayed second opinion.
Once skrabe publishes a version that was pinned at rung 3, compare their JSON against the frozen local corpus. A mismatch flags for review; it never halts the run.

Updates - 2026-08-24 upgrade-path orientation session

The molt (#18) and the pilot's "Pass 2" are different artifacts; do not conflate them.
The molt is a static text diff: the override pack against stock prompt text at 2.1.204 and again at 2.1.241, classifying each override. It runs zero live models and measures no behavior - text against text, inherently one-dimensional. "Pass 2" is a live A/B benchmark run. The "compared across too many dimensions" critique applies to Pass 2, never to the molt.
Surfaced 2026-08-24 when Jeremy asked whether #18 was premature for "comparing across too many dimensions" - he had merged the molt with the pilot's Pass 2. Separating them changed every downstream answer.
The molt detects drift; deciding what to do with the drift is a separate, downstream step.
Molt = understanding what changed moving current -> new. Acting on it (resolve the 365 review findings, carry the pack forward, or drop it) is a distinct decision, gated on evidence the molt itself does not produce.
Jeremy restated this himself and asked "I think that means we agree?" - it does.
Pass 1 and Pass 2 are the two live benchmark runs in the pilot (issues #8/#16), scaffolded in pilot/pass1/ and pilot/pass2/.
Pass 1: the 12 curated tasks fired stock SP vs lobotomized SP, both panes claude-opus-4-8, both on 2.1.204 - one variable, the system prompt. This IS "the dozen lobotomized tests." Pass 2 (as originally defined): whole-stack comparison, current install (2.1.204 + lobotomized + opus-4-8) vs fresh out-of-box (2.1.241 + stock + new model) - three variables at once.
Bundled Pass 2 cannot attribute its result; that is the confound to design out.
If out-of-box wins, you cannot tell whether the new model, the version bump, or dropping the pack caused it - and those point at opposite conclusions about whether to keep the lobotomized pack. A bundled comparison is a fair product go/no-go ("upgrade at all?") but the wrong instrument for measuring impact one variable at a time.
Pass 1 is independent of #18, so #18 is parked behind it.
Pass 1 runs on 2.1.204 where the lobotomized pack is already native - no molt needed. Pass 1 answers "does lobotomized work." If no, the 365 findings are moot (upgrade to stock). If yes, the molt becomes the mechanism to realign the pack to 2.1.241. So run Pass 1 first, then decide on #18.
Jeremy's own instinct ("should it be parked until the dozen lobotomized tests can be run?") - confirmed correct with the dependency logic, not just agreed to.
The clean new-stack SP test is the comparison that is missing, and it is gated on #18.
To isolate the SP where it will actually run: {2.1.241 + new model + stock SP} vs {2.1.241 + new model + molted-lobotomized SP} - Pass 1's one-variable logic moved onto the new stack. It cannot run until the molt (#18) produces a valid 2.1.241 pack, because the pack is tuned for opus-4-8 against 2.1.204 stock.
Upgrade-need a-2 (comprehend what changed in stock CC + skill compatibility) is served by neither the molt nor the pilot.
The molt is override-centric; the pilot measures behavior. Neither answers "what did stock Claude Code itself change 2.1.204 -> 2.1.241, and does it break or make redundant my skills and workflows." Filed as issue #19 (wayfinder:research). Raw material already exists: corpora/2.1.204 and corpora/2.1.241 support a stock-vs-stock diff, and /loop-molt covers the skill-compatibility half.
Curating the 12 tasks (Task 5) is the real current blocker, and it is a human-judgment gate.
A script (pilot-mine-tasks.py) surfaces candidate tasks from real past sessions (zero spend, local read), labeling each quick (≤5 assistant turns) or multi. You pick 12 per pass, stratified, choosing tasks that exercise the SP rather than flatter it. Each pick becomes pilot/tasks/<id>/ with prompt.md (verbatim human turns, replayed identically to both panes so only the SP differs), checklist.md (done-conditions each with the exact proving command/output), and input/ (a byte-identical fixture reset before each pane).
The instrument (#8/#16) is built and closed, but no tasks are curated - pilot/tasks/ holds only README and TEMPLATE. This step, plus live spend, is what stands between "built" and "Pass 1 can fire."
The scrub gate is a hard, structural PII control, not a cleanup step.
Real-session tasks carry donor/advancement/PII data. Names, IDs, amounts, and queries are synthesized (shape preserved) before a packet leaves its host. Raw day-job prompt text never transits off its governed host; only a --no-text candidates file (shape counts, no content) may travel. pilot/tasks/ is gitignored, so a packet enters git only by explicit git add -f after passing the gate - two deliberate actions, gate first.

Updates - 2026-09-07 global launcher justfile session: how the setup works

 interactive shell (~/.zshrc sources ~/.zsh.d/*.zsh)
        |
   alias jr='just -g'          non-interactive shells never source ~/.zshrc,
        |                      so scripts always see the real binaries
        v
 ~/.config/just/justfile   (the -g global justfile, runnable from any cwd)
        |
        +-- bare launchers: cc, pi, cdx
        |     direct #!/usr/bin/env bash recipes ending in  exec <binary> ... "$@"
        |     real flags pass through intact:  jr cc --resume abc123
        |
        +-- 12 role combos: {cc,pi,cdx}-{content,design,writing,code}
              one-liners forwarding to a core:  cc-content *args: (_claude "content" args)
              the variadic collapses to ONE word, so combos carry prose prompts only
        |
        v
   cores _claude / _pi / _codex   (one per program, holding its injection quirk)
     _claude: claude --dangerously-skip-permissions --append-system-prompt-file <stub>
     _pi:     pi --append-system-prompt <stub path>        (pi has no skip-perms flag)
     _codex:  bash core cats the stub into the prompt text  (option c, no config key)
        |
        v
   ~/.config/jjr/prompts/{content,design,writing,code}.md   (role stubs, inert markers
   until real prompts are authored - jr cc-content is jr cc plus a marker line today)

 management:  ~/.config/just/launcher.py  status | tool add/remove | stub add/remove
   parses the justfile as the single source of truth (no registry of its own),
   validates every edit with `just --list`, and rolls back if parsing breaks
The whole launcher moves as one unit.
Everything lives under $HOME with no absolute paths beyond it: ~/.config/just/justfile, ~/.config/just/launcher.py, ~/.config/jjr/prompts/, and ~/.zsh.d/just.zsh. Designed for the parked dotfiles-repo move.
Two recipe shapes exist on purpose; do not unify them.
just's dependency-argument passing collapses a variadic into a single string, so a forwarded recipe structurally cannot deliver --resume abc123 as two arguments. Bare launchers are therefore direct shebang recipes with a real "$@"; combos forward and carry one quoted prose prompt. Verified on just 1.58.0.
Rubix high finding, 2026-09-07: the draft's 15-recipes-over-3-cores design would have silently sent a resume session id to the model as prose - the worst failure given how often quota kills sessions.
The codex core is the fallback body; the append-vs-replace question is still open.
The probe never reached a model turn: the host's stored codex key returns 401 Unauthorized. Option (c) (cat the stub into the prompt) needs no config key, so it went live, with the truthful verdict recorded as a comment in the justfile (line 32). The retry is staged in the 2026-09-07 batch-review journal; after codex login, an APPEND verdict means swapping _codex to the option (a) model_instructions_file body.

Updates - learnings (2026-09-07)

The alias is jr, not jq - the remembered "jq" name collided with the real JSON tool.
Jeremy caught that jq is /usr/local/bin/jq. The overlap fails dirty, not clean: just -c runs an arbitrary command and just -e opens an editor, so a reflexive jq -e '.x' file.json would do something other than error. Renaming beat shadowing-with-escape-hatches.
"zsh aliases do not expand in scripts" was asserted, reviewed, and found false.
The real containment is that non-interactive zsh never sources ~/.zshrc. The draft plan justified the jq collision with the false version; the rubix pass corrected it, and the jr rename later made the whole question moot.
A near-miss worth keeping: a comforting mechanism claim survived until someone tested it, and the true mechanism had different edge cases.
grep -Ec counts matching lines, not occurrences, and [0-9]+ fail matches "0 fail".
The draft plan's zero-spend verification gate returned 1 in every case and could never discriminate pass from fail. Replaced with numeric extraction.
Rubix critical finding, 2026-09-07. A verification gate that always passes is worse than no gate.
A smoke check that asks a session to echo its injected instructions can be refused as injection-probing.
claude refused the plan's marker-echo phrasing twice while the refusal itself quoted the stub file, proving injection worked. The check phrasing was the bug, not the plumbing; one reworded probe passed.
A review finding that contradicts a decision the brief settles in writing gets its documentation half only.
Both rubix lenses independently wanted the skip-permissions default inverted. The brief says "skip-permissions flags are baked in", so the executor folded in blast-radius documentation and warning comments, left the default alone, and logged the reasoning.
argparse rejects dash-leading option values in space form; require the = form.
launcher.py tool add ... --prompt-flag --system-prompt-file fails ("expected one argument"); --prompt-flag=--system-prompt-file works. Documented in the script's help, since prompt flags always start with a dash.
launcher.py's stub remove refuses to delete authored prompts without --force.
A file still containing ROLE-STUB-MARKER or the placeholder comment deletes freely; anything else is treated as authored content. The one guard kept, because roles will eventually hold real prompts and stub remove design nuking one is data loss.

Updates - key decisions register (2026-09-07)

DecisionAlternatives consideredWhy
Shell alias renamed to jr Keep jq and reach the JSON tool via \jq / command jq The flag overlap (-c, -e, -f, -s, -n) fails dirty at an interactive prompt; jr was free on the host (verified with type jr).
launcher.py parses the justfile as its single source of truth Script-owned registry or config file; full justfile regeneration from a template No second state to drift, and hand-tuned recipe bodies (the codex bash core, warning comments) survive edits untouched.
Every launcher.py justfile edit is validated by just --list and rolled back on failure Write and hope; unit tests on the parser just itself is the only authority on whether the file still parses; one subprocess call, zero test scaffolding.
tool add generates only the path-flag injection style Support codex-style cat-into-arg cores via templates claude and pi shaped tools cover the common case; a codex-shaped core is hand-written once and the script manages it fine afterward. Deliberate ceiling.
Bare launchers are shebang recipes; role combos forward to cores All 15 recipes forwarded through cores (the draft design) Forwarding collapses variadics, breaking flag pass-through; see the learnings entry. The split preserves jr cc --resume <id>.
Skip-permissions flags stay baked in for claude and codex Invert to safe-by-default with -danger variants (both rubix lenses wanted this) The brief settles it in writing; a review finding does not overturn a written user decision. Warning comments and blast-radius notes were folded in instead.
